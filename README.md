# 자취방정식 (jb-front)

라이프스타일 기반 주거 매물 추천 서비스의 **모바일 웹앱** 프론트엔드.

단순 위치·가격 검색을 넘어, **통근 효율성(1차)** 과 **생활 환경 가중치(2차)** 를 결합해
100점 만점의 개인화된 **매칭 점수(Match Score)** 를 산출한다.

## 기술 스택

| 영역       | 선택                                      |
| ---------- | ----------------------------------------- |
| 프레임워크 | Vue 3 (`<script setup>`, Composition API) |
| 빌드       | Vite                                      |
| 언어       | TypeScript (strict)                       |
| 상태       | Pinia                                     |
| 라우팅     | Vue Router (history mode)                 |
| 스타일     | Tailwind CSS v4                           |

## 실행

```bash
npm install
npm run dev   # http://localhost:5173
```

| 스크립트             | 설명                            |
| -------------------- | ------------------------------- |
| `npm run dev`        | 개발 서버                       |
| `npm run build`      | 타입 체크 + 프로덕션 빌드       |
| `npm run preview`    | 빌드 결과 미리보기              |
| `npm run type-check` | 타입 체크만 (`vue-tsc --build`) |
| `npm run format`     | Prettier 포매팅                 |

### 환경 변수

**커밋되는 env 파일은 없다.** 키는 두 군데서 온다:

- **배포** — 호스팅(Cloudflare) **빌드** 환경변수. 런타임 변수 쪽에 넣으면 빌드 때 안 읽혀
  빈 값으로 굳는다
- **로컬** — 직접 만드는 `.env.local` (gitignore 대상)

`VITE_` 값은 **어디에 넣든 빌드 결과에 평문으로 박힌다** — 대시보드에 넣어도 마찬가지다.
그래서 여기 있는 건 전부 공개를 전제로 한 식별자고, 방어는 값을 숨기는 게 아니라
**각 콘솔의 도메인 제한**이 한다. 판단 기준은 `docs/env-and-secrets.md`.

로컬 개발용 `.env.local` 템플릿:

```bash
# 카카오 JavaScript 키 (REST·Admin 키 아님)
VITE_KAKAO_MAP_KEY=

# 구글 웹 클라이언트 ID. 백엔드 GOOGLE_CLIENT_ID 와 **같은 값**이어야 한다
VITE_GOOGLE_CLIENT_ID=

# 로컬 백엔드로 붙일 때만. 기본은 배포 백엔드(vite.config.ts)
# API_PROXY_TARGET=http://localhost:8080
# API_PROXY_ORIGIN=http://localhost:5173   # 백엔드 AUTH_ALLOWED_ORIGINS 에도 추가
```

| 키 | 없으면 |
| --- | --- |
| `VITE_KAKAO_MAP_KEY` | 지도가 자리표시자로 동작 |
| `VITE_GOOGLE_CLIENT_ID` | 비로그인으로 동작 (로그인 팝업이 막힘) |
| `VITE_API_BASE_URL` | 같은 오리진 — 개발에선 Vite 프록시가 받는다 |
| `API_PROXY_TARGET` · `API_PROXY_ORIGIN` | 배포 백엔드로 붙는다 |

**키가 없어도 앱은 뜬다** — 지도는 자리표시자가 되고 로그인은 막힌다. 다만 거점 검색은
카카오 SDK 를 그대로 부르므로 키 없이는 실패 안내가 뜬다(가짜 데이터로 받아 주던 목을
걷어냈다).
그래서 클론 직후 `npm install && npm run dev` 가 바로 된다.

> `API_` 로 시작하는 둘은 `VITE_` 가 없어서 **번들에 안 들어간다** — 개발 서버만 본다.
>
> ⚠️ **백엔드 env 를 여기 두지 않는다.** DB 암호·JWT 서명키·외부 API 키는 프론트가
> 가질 값이 아니다(`docs/env-and-secrets.md` 3단계).

## 디렉터리 구조

```
src/
├── assets/       # main.css — Tailwind 테마 토큰 + 모바일 베이스 스타일
├── components/   # 화면 조각. 하위 폴더 없이 평평하게 둔다
├── lib/          # 도메인에 기대지 않는 함수·상수 (포맷·정렬·점수 구간·SDK 로더 등)
│   └── api/      #   서버 호출. 응답 → 도메인 타입 변환도 여기서 한다
├── pages/        # 라우트 단위 화면
├── router/       # 라우트 정의
├── stores/       # Pinia 스토어
└── types/        # 도메인 타입
```

### 컴포넌트는 폴더로 나누지 않고 이름으로 구분한다

`components/` 는 평평하다. 기능별(`features/`)로도, 범용/특화(`ui/`)로도 쪼개지 않는다.
대신 **도메인을 모르는 부품에는 `Base` 접두사**를 붙인다 — Vue 스타일 가이드의 방식이다.

```
BaseBottomSheet  BaseChip  BaseRangeSlider
BaseScoreDonut   BaseSegmentedControl  BaseWeightSlider   ← 도메인 무지
ListingCard  FilterPanel  MapView  WelcomeOverlay  …      ← 도메인을 안다
```

폴더 대신 이름을 쓰는 이유:

- 알파벳 정렬이 알아서 한 덩어리로 모아준다. 폴더 없이도 목록에서 뭉쳐 보인다
- 성격이 바뀌어도 **파일을 옮기지 않는다** — import 경로가 깨지지 않는다

판별 기준은 하나다. **`@/stores` · `@/types` · `@/lib/api` 를 import 하는가.**
안 하면 `Base` 다. `BaseScoreDonut` 은 `score: number` 만 받고 그게 매칭 점수인지 모른다.
`ListingCard` 는 `Listing` 을 알므로 아니다.

경로 별칭 `@` 는 `src/` 를 가리킨다 (`vite.config.ts`, `tsconfig.app.json` 양쪽에 정의).

## 모바일 전용 설계

이 앱은 **모바일 전용**이다. 데스크톱 브레이크포인트를 쓰지 않고, 어떤 화면 폭에서도
`--spacing-shell`(480px) 폭의 앱 셸을 중앙에 고정한다.

- 노치 대응: `safe-top` / `safe-bottom` 유틸리티 (`env(safe-area-inset-*)`)
- iOS 확대 방지를 위해 폼 컨트롤 최소 폰트 16px, 터치 타깃 최소 높이 44px
- `sm:` `md:` `lg:` 접두사는 사용하지 않는다
- 화면 좌상단 아이콘 버튼(뒤로·닫기)은 **헤더 `px-2 pt-3` + `size-11` + `size-6` 아이콘** —
  터치 타깃 44px 을 지키면서 아이콘의 광학 왼쪽 여백이 지도 상단 바와 같은 18px 이 되고,
  위로는 안전영역에서 12px 띄워 아이콘 중심이 34px 에 선다(시안 실측 ~37px).
  화면마다 다른 값을 쓰면 화면을 옮길 때 뒤로 화살표가 좌우·위아래로 튄다

### 대응 화면 폭

| 구간 | 동작 |
|---|---|
| ~ 319px | **미대응** |
| **320px ~ 479px** | 앱 셸이 화면 폭을 100% 채운다 |
| **480px 이상** | 셸이 480px 에서 고정되고 양옆은 회색 여백 |

- 하한은 **320px** — iPhone SE(1세대) 세로 폭. 이보다 좁은 기기는 대응하지 않는다
- **상한은 없다.** 27인치든 4K든 480px 셸이 중앙에 고정되므로 레이아웃이 더 바뀌지 않는다
- 브레이크포인트를 쓰지 않는 이유가 이것이다 — 폭에 따라 바뀔 레이아웃 자체가 없다

320px 에서 가장 빠듯한 건 매물 카드다. 썸네일 80px + 점수 도넛 64px + 열 사이 여백까지
**고정으로 168px** 을 먹고(목록 좌우 패딩 40px 을 더하면 208px), 320px 에서 본문에 남는
폭은 **112px** 뿐이라 나머지를 `truncate` 로 흡수한다.
카드에 요소를 더 얹을 때는 이 여유부터 확인한다.

세로는 `dvh` 기준이라 별도 하한을 두지 않는다. **가로모드는 대응 대상이 아니다.**

## 역할 분담

도메인 모델 설계와 매칭 점수 계산은 **백엔드가 수행한다.** 프론트는 사용자가 설정한 조건을
백엔드로 보내고, 계산되어 내려온 점수와 매물을 표시한다.
점수 산식과 도메인 타입 정의는 프론트에 두지 않고, API 스펙에 맞춰 가져다 쓴다.

| 주체   | 담당                                                                           |
| ------ | ------------------------------------------------------------------------------ |
| 프론트 | 거점·가중치·필터 입력 UI, 요청 전송, 결과 표시                                 |
| 백엔드 | 도메인 모델 설계, 이동 효율성 측정, 생활환경 지표 산출, 매칭 점수 계산 및 정렬 |

## 포맷 유틸

`src/lib/format.ts` — 만원 → "1억 2,000", ㎡ → 평, 분 → "1시간 20분" 등
한국 부동산 표기 변환. 도메인 타입에 의존하지 않는 숫자 → 문자열 변환만 담당한다.

`src/lib/listing-sort.ts` — 목록 정렬 **키·라벨과 줄 세우는 법**.
매물 목록 API 가 영역(bbox) 조회라 한 번에 다 주고 정렬 파라미터를 받지 않아서
(jb-backend `property-listing-and-detail.md`), **화면이 직접 정렬한다.**
가격 축을 환산보증금(보증금 + 월세×100)으로 흉내 내는 임시 규칙도 여기 있다 —
가격 축의 정의는 원래 백엔드 몫이라(위 '역할 분담'), 서버가 정렬 키를 받기
시작하면 지우고 그 키를 넘긴다.

`src/lib/listing-list.ts` — 목록 한 벌의 상태(받아오기·정렬).
**페이지가 없다.** 지도 핀과 바텀시트 목록이 같은 한 벌을 쓴다 — 둘로 나눠 받으면
같은 순간에 지도와 목록이 서로 다른 매물을 보여줄 수 있다.
